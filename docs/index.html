Contributing to TransitDen

TransitDen is an open-source real-time and historical transit tracker for Denver's RTD network. Contributions of all kinds are welcome — bug fixes, new features, documentation, and more.

What is TransitDen?

TransitDen polls RTD's GTFS-RT protobuf feeds every 30 seconds, stores all vehicle positions and trip updates in TimescaleDB, and serves a live map and analytics dashboard. The goal is to give Denver riders and transit enthusiasts a transparent look at real-time performance data that RTD doesn't surface anywhere else.

Key features:

  • Live map of all RTD light rail, commuter rail, and Flatiron Flyer buses
  • On-time performance tracking and delay alerts
  • Historical trip drill-down by line, vehicle, and time window
  • Frequency and headway analytics dashboard

Tech Stack

Frontend

Next.js 14 (App Router) React 18 TypeScript Tailwind CSS TanStack Query Leaflet Recharts Vitest

Backend

Branch Strategy

The project uses three long-lived branches. All contributor work should start from dev and be submitted back to dev.

main Production

Auto-deploys to the live site on every push. Docker images are tagged :latest. Do not open PRs directly to main.

staging Staging

Auto-deploys to the staging environment. Docker images are tagged :staging. Used to verify changes in a production-like environment before merging to main.

dev Development

Local testing only — no auto-deploy. This is where new features and bug fixes land first. All contributor PRs should target dev.

Feature & fix branches

Branch off dev using a descriptive name that signals intent: 

# New feature
git checkout -b feat/trip-drill-down dev

# Bug fix
git checkout -b fix/headway-rounding dev

# Documentation
git checkout -b docs/contributing-guide dev

Local Setup

Prerequisites

  • Docker + Docker Compose (recommended — handles DB, backend, and frontend together)
  • Node 20+ (for frontend-only work)
  • Python 3.13 (for backend-only work)

Full stack (recommended)

This is the fastest way to get everything running:

git clone https://github.com/ImMattic/transitden.git
cd transitden
git checkout dev
docker compose up --build

The backend auto-runs Alembic migrations and starts the GTFS-RT polling loop on startup. The frontend is available at http://localhost:3000 and the API at http://localhost:8000.

Frontend only

cd frontend
npm install
BACKEND_URL=http://localhost:8000 npm run dev

Backend only (no Docker)

cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r ../requirements.txt
export DATABASE_URL=postgresql+asyncpg://transitden:transitden@localhost:5432/transitden
alembic upgrade head
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
ℹ️

GTFS static data — the gtfs-static/ directory contains bundled RTD feed CSVs (routes, stops, shapes). These expire roughly quarterly. If on-time performance shows 0% across the board, the feeds likely need refreshing.

PR Workflow

  1. Fork or clone the repo, then check out dev as your base branch.
  2. Create a branch with a descriptive name following the feat/ or fix/ convention described above.
  3. Make your changes. Keep commits focused — one logical change per commit makes review easier.
  4. Test locally. Run the full stack and manually verify your change works as expected. See Running Tests below.
  5. Open a pull request targeting dev. Describe what you changed and why. If it fixes a bug, link the relevant issue or describe the repro steps.
  6. CI must pass — the GitHub Actions workflow runs backend pytest, frontend lint, TypeScript type-check, and Vitest on every PR.
⚠️

Do not open PRs directly against main or staging. Both are managed by the project maintainers after changes have been validated on dev.

Running Tests

Backend (pytest)

Tests run with an in-memory SQLite database — no running Postgres needed:

python -m pytest tests/ -v --tb=short

Or via Docker:

docker compose exec backend pytest tests/ -v --tb=short

Frontend (lint + type-check + Vitest)

cd frontend

# Lint
npm run lint

# TypeScript type check
npx tsc --noEmit

# Unit tests
npm test
✅

All three frontend checks (lint, tsc, vitest) and backend pytest run automatically via GitHub Actions on every push and pull request. A passing CI is required before merging.

Database Migrations

The project uses Alembic for schema migrations. If you change any SQLAlchemy models, generate and commit a migration file: 

# Generate a migration after editing models
docker compose exec backend alembic revision --autogenerate -m "describe your change"

# Apply all pending migrations
docker compose exec backend alembic upgrade head

Migration files live in backend/alembic/versions/. Always review auto-generated migrations before committing — Alembic doesn't always detect every change correctly, especially TimescaleDB-specific constructs.

Contributor Guidelines

TransitDen is a community project. To keep things running smoothly, please follow these guidelines:

Reporting bugs & requesting features

Before writing any code, please check the GitHub Issues tab to see if your bug or feature request has already been reported.

  • Bug reports — open an issue with a clear title, steps to reproduce, what you expected, and what actually happened. Include your browser and OS if it's a frontend issue.
  • Feature requests — open an issue describing the feature and the problem it solves. Discussing the idea first avoids duplicate effort and ensures it fits the project's direction before anyone writes code.
  • If you're planning to work on something yourself, comment on the issue to claim it so others know it's being handled.

General

  • Test in a local environment before opening a PR. Running docker compose up --build and verifying your change in a browser is the minimum bar. Don't rely solely on "it compiles" — check the golden path and any affected edge cases.
  • Keep pull requests focused. A PR that fixes one bug is easier to review than one that fixes a bug and refactors half the codebase.
  • Write clear PR descriptions. Explain the why, not just the what. Screenshots or short screen recordings for UI changes are appreciated.
  • If you're picking up an existing issue or TODO item, mention it in your PR description and link the issue number.
  • Be respectful and constructive in code review. We're all here to build something useful for Denver transit riders.

Scope

  • TransitDen explicitly has no user accounts or authentication — please don't add any.
  • Changes to CI/CD pipelines, deployment configs, or infrastructure files (docker-compose.yml, .github/workflows/) should be discussed in an issue first.
  • If you're unsure whether a feature fits the project's direction, open a GitHub issue to discuss before writing code.

AI Contributions

🤖

AI contributions are welcomed and encouraged. A significant portion of this codebase was written with the assistance of AI tools. If you use an AI coding assistant (Claude, Copilot, Cursor, etc.) to help write or review your contribution, that's great — just hold it to the same standard as human-written code.

When using AI assistance, please:

  • Always test AI-generated code in a real local environment before submitting. AI tools can produce code that looks correct but subtly breaks existing behavior — catching that requires actually running the app.
  • Review AI-generated diffs before staging them. You're responsible for what goes in your PR, regardless of who (or what) wrote it.
  • Don't blindly apply large AI-generated refactors outside the scope of your change. Keep PRs focused.
  • If an AI tool suggests a change to a migration, a CI workflow, or an infrastructure file, double-check it carefully — these are the areas where subtle errors have the most impact.

Code Style

Frontend (TypeScript / React)

  • TypeScript strict mode — no any without a good reason
  • ESLint enforced via npm run lint
  • Tailwind CSS for styling; avoid inline styles
  • Prefer server components where possible; use "use client" only when needed (interactivity, browser APIs)
  • TanStack Query for all data fetching — don't call fetch directly in components

Backend (Python)

  • Python 3.13+ — use modern syntax (match, union types, etc.)
  • Async everywhere — all database calls go through AsyncSession
  • Pydantic schemas for request/response validation
  • No linter is enforced in CI yet, but ruff and mypy are recommended locally

Commits

  • Use the imperative mood: "Add trip drill-down endpoint" not "Added…"
  • Prefix with fix:, feat:, docs:, refactor:, or chore: when it helps clarity
  • Keep the subject line under 72 characters
